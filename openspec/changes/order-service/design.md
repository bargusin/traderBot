## Context

Текущее состояние: бот использует 5 из 12 сервисов Tinkoff InvestAPI (MarketDataService, InstrumentsService, OperationsService, UsersService, SandboxService). Команды `/portfolio`, `/price`, `/chart` работают в async-стиле с `CompletableFuture`. Multi-step флоу реализуются через `InputHandler` + `UserStateService`. Ордера currently не поддерживаются — в codebase есть только демо-класс `TradingService` с хардкодом, не интегрированный в бот.

## Goals / Non-Goals

**Goals:**
- Реализовать `TradingService` в core как обёртку над InvestAPI `OrdersService`
- Добавить команды `/purchase`, `/sell` с multi-step flow (тикер → количество → подтверждение → результат)
- Добавить команду `/orders` с просмотром активных и исполненных ордеров + кнопка отмены
- Поддерживать как MARKET, так и LIMIT ордера
- Добавить юнит-тесты для нового функционала

**Non-Goals:**
- Стриминг статусов ордеров в реальном времени (OperationsStreamService)
- Стоп-ордера (StopOrdersService)
- Автоматические торговые стратегии
- Торговые рекомендации / аналитика

## Decisions

### 1. Async API, не Sync

**Выбор:** Использовать async-методы InvestAPI (`postOrder`, `cancelOrder`, `getOrders`) вместо sync-вариантов.

**Почему:** Consistent с существующим стилем бота (PortfolioCommand, PriceCommand, ChartCommand все используют `CompletableFuture`). Sync-методы блокируют поток.

**Альтернатива:** Sync + `@Async` аннотация — отвергнута, т.к. добавляет сложность без выигрыша.

### 2. Multi-step flow через InputHandler

**Выбор:** Multi-step флоу (тикер → количество → подтверждение) через последовательные `InputHandler`-ы.

**Почему:** Уже используется в `ChangeTokenCommand` для смены токена. Единый паттерн, проверенный в codebase.

**Альтернатива:** One-shot команда `/purchase AAPL 10` — проще, но не даёт пользователю увидеть расчёт стоимости и подтвердить сделку. Решено: поддержать оба варианта (с аргументами и без).

### 3. Подтверждение через inline-кнопки

**Выбор:** Кнопки "Подтвердить" / "Отмена" для финального подтверждения ордера.

**Почему:** Визуально直观, пользователь видит итоговый расчёт перед исполнением. Inline-кнопки уже используются в боте (chart period, account switch).

### 4. Типы ордеров: MARKET по умолчанию, LIMIT опционально

**Выбор:** По умолчанию рыночный ордер. Лимитный — через аргумент или inline-кнопку "Лимитный" с вводом цены.

**Почему:** Рыночные ордера проще для пользователя. Лимитные требуют дополнительного шага (ввод цены), но важны для контроля исполнения.

### 5. Кеширование getMaxLots/getOrderPrice

**Выбор:** Кешировать результаты `getMaxLots` и `getOrderPrice` на короткий TTL (30 сек), как в `MarketDataService`.

**Почему:** Эти методы вызываются при каждом шаге flow. Кеш снижает нагрузку на API и ускоряет отклик.

### 6. Отдельный класс для обработки callback-ов ордеров

**Выбор:** Вынести обработку callback-ов (`confirm_order`, `cancel_order`, `switch_order_type`) в отдельный `OrderCallbackHandler`, а не держать в каждой команде.

**Почему:** Callback-ы `confirm_order#BUY_AAPL_10` и `cancel_order#12345` обрабатываются из разных команд (`/purchase`, `/sell`, `/orders`). Единый handler проще поддерживать.

### 7. Отображение ордеров: активные + история

**Выбор:** `/orders` показывает активные ордера по умолчанию. Inline-кнопка "История" переключает на исполненные.

**Почему:** Активные ордера — основной интерес (можно отменить). История — справочная информация.

## Risks / Trade-offs

- **[Риск] Ошибка исполнения ордера** → Показать пользователю статус и причину. Не повторять автоматически.
- **[Риск] Недостаточно средств** → `getOrderPrice` покажет предварительную стоимость перед подтверждением. Проверка maxLots предотвращает заказ больше доступного.
- **[Риск] Лимитный ордер не исполняется** → Показать статус "В очереди". Предложить отмену через `/orders`.
- **[Trade-off] Нет стриминга** → Статус ордера обновляется только при запросе `/orders`. Для MVP это приемлемо.
- **[Trade-off] Нет стоп-ордеров** → Вынесено за рамки MVP. Может быть добавлено позже.
