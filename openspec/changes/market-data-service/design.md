## Контекст

Бот построен на 3-модульной Gradle-архитектуре: `core` (базовые сервисы), `bot` (Telegram-интерфейс), `strategy` (пустой). Tinkoff InvestAPI SDK 1.27 уже интегрирован через `TradingSessionManager` (создание `InvestApi` по токену) и `ApiCallExecutor` (обработка ошибок). Рыночные данные (`MarketDataService` SDK) пока нигде не используются.

Текущие команды (`/start`, `/portfolio`, `/account`, `/settings`) работают через `AbstractCommand` с общими хелперами `buildHeaderText()`, `backToMainKeyboard()`. Все команды регистрируются в `MessageHandler`.

## Цели / Не-цели

**Цели:**
- Предоставить доступ к рыночным данным (свечи, цены, стакан, статус торгов) из Telegram-бота
- Кешировать запросы к API для снижения нагрузки и соблюдения rate limits
- Поддерживать три режима работы (SANDBOX/READONLY/PRODUCTION) через существующий `TradingSessionManager`
- Асинхронные вызовы SDK (CompletableFuture) без блокировки потоков бота

**Не-цели:**
- Торговые стратегии (отдельный модуль `strategy`, будет позже)
- Размещение ордеров через MarketDataService (это для OrdersService)
- WebSocket-стриминг (будет в фазе 4, сейчас достаточно polling-запросов)
- Рендеринг графиков как изображений (Telegram не поддерживает, используем текстовый формат)

## Решения

### 1. Текстовый формат графиков вместо изображений

**Выбор:** Форматировать свечи как ASCII/text-блок с использованием символов ▁▂▃▄▅▆▇█

**Альтернативы рассмотрены:**
- PNG-графики через библиотеку (JPint, XChart) — отклонено: требует тяжёлые зависимости, сложности с отправкой файлов через Telegram API, проблемы с памятью
- Inline-фото через URL (TradingView) — отклонено: нестабильно, требует внешний сервис

**Обоснование:** Текстовый формат нативно работает в Telegram, не требует зависимостей, мгновенно отображается.

### 2. Кеш на основе ConcurrentHashMap с TTL

**Выбор:** In-memory кеш в `MarketDataService` с TTL 60 секунд для цен, 300 секунд для свечей, 600 секунд для стакана.

**Альтернативы:**
- Redis/Memcached — отклонено: избыточно для одного пользователя, добавляет инфраструктуру
- Guava Cache — отклонено: не хочет тянуть зависимость ради одного класса
- Кеш без TTL — отклонено: данные устареют, пользователь увидит неактуальную цену

**Обоснование:** `ConcurrentHashMap` + `System.currentTimeMillis()` TTL — минималистичное решение, потокобезопасное, без внешних зависимостей.

### 3. Разделение на core-сервис и bot-команды

**Выбор:** `MarketDataService` в `core` (чистый сервис, без Telegram-зависимостей), команды `/chart` и `/price` в `bot`.

**Альтернативы:**
- Всё в `bot` — отклонено: нарушает архитектуру, невозможно переиспользовать в `strategy`
- Всё в `core` — отклонено: core не должен знать о Telegram

**Обоснование:** Сохраняет текущую архитектуру, позволяет модулю `strategy` использовать `MarketDataService`.

### 4. Интерфейс инструмента по тикеру

**Выбор:** `/chart AAPL` → `findInstrument("AAPL")` → `getInstrumentByFigi(figi)` → MarketDataService

**Альтернативы:**
- Прямой ввод FIGI — отклонено: пользователь не знает FIGI
- Поиск по UID — отклонено: UID ещё менее удобен

**Обоснование:** Тикер — самый узнаваемый идентификатор для пользователя.

## Риски / Компромиссы

- **Rate limits Т-Банка** → Кеш с коротким TTL (60с для цен) минимизирует количество запросов. При превышении лимита — логируем предупреждение.
- **Нет real-time обновлений** → Текущее решение — polling по запросу пользователя. WebSocket-стриминг будет добавлен позже.
- **Текстовые графики ограничены** → Для 50+ свечей текст будет длинным. Ограничим максимальное количество свечей (100), предложим выбор периода через inline-кнопки.
- **Кеш может занимать память** → При большом количестве тикеров. Ограничим размер кеша (max 500 записей) с eviction по FIFO.
